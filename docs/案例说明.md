# 案例说明｜三个关键决策/产出是怎么做出来的

**用途**：配套 `docs/AAR.md` 使用，说明本项目三个关键决策或产出是如何在人机协作中形成的。

**选取标准**：三个案例分别代表三种协作形态 —— **定架构约束 / 定质量标准 / 纠方向**，
避免同类型重复。三例的主体均为**项目负责人**的判断与介入。

**证据原则**：每例均给出「原文 · prompt · 产出 · 对比」四段，标注证据出处
（文件位置、命令输出、原话）。所有对比数字均来自实际执行，可复现。

| 案例 | 你的发现形态 | 关键决策/产出 | 一句话效果 |
|---|---|---|---|
| 案 1 | 一条约束定架构 | 翻译队列脚本的设计路线 | 排除了整条 API 路线 |
| 案 2 | 划定质量标准 | README 数字改为可溯源 | manifest 引用 0 → 17 处 |
| 案 3 | 纠方向 | 术语表改为从新语料重建 | 零槽位术语 98 → 0 |

## 案 1｜「无密钥无额度」一句话决定了整条技术路线

### ① 原文（当时的岔路口）

翻译环节在设计上存在两条互斥的路线：

| 路线 | 做法 | 代价 |
|---|---|---|
| ① 接入大模型 API | 脚本调用 API 自动翻译 | 需要密钥与额度；译文质量与一致性难以逐篇验收 |
| ② 人译 + 脚本做队列 | 脚本负责排队、生成 prompt、校验、落盘 | 翻译速度受限于人；但每篇可独立验收 |

当时的默认倾向是路线 ①（自动化程度更高）。**路线 ② 的确定，来自负责人给出的约束。**

### ② 你的 prompt

> 「`translate_queue.py` 只要队列管理」
>
> 「**无密钥无额度**」

这是一条**约束型指令**，而不是功能描述。它没有说明「脚本应该做什么」，
而是划定了「不能依赖什么」—— 直接排除了路线 ①。

### ③ 产出

`scripts/translate_queue.py` —— 一个翻译工作队列管理器。

其模块声明如实记录了这条约束：

```
定位
    ⚠️ 本脚本【不调用任何大模型 API】（无密钥/额度）。翻译动作由人完成，
       脚本负责：排队 → 生成精准 prompt → 严格校验 → 落盘 → 留痕 → 进度。

为什么按【文档】为单位排队，而不是整篇丢给 AI
    一篇最多约 99,000 字符。一次性翻译会让 AI 悄悄跳过中间部分，
    而且返回值看起来是完整的（最危险）；一处错了无法定位，也无法逐篇验收。
    所以一篇一次调用，每篇独立验收。
    > 20000 字符的文档允许在【标题边界】折成 2-3 段，但每段带文档 ID 和段序号。
    ⚠️ 不按字数硬切。
```

配套产生的关键机制：`save` 子命令是**硬闸门**，四项校验（代码块逐字节一致、
URL 全保留、标题行数一致、长度比在区间）任一不过即拒收。

### ④ 对比（改前 vs 改后）

| 项 | 路线 ①（未采用） | 路线 ②（实际实现） |
|---|---|---|
| 大模型 API 调用 | 是 | **0 处** |
| 密钥依赖 | 必需 | **无** |
| 翻译执行者 | 脚本 | 人 |
| 脚本身份 | 翻译器 | 排队 / 生成 prompt / 校验 / 落盘 / 留痕 / 进度 |
| 逐篇验收 | 难以定位错误 | `save` 硬闸门，四项校验不过即拒收 |

### ⑤ 证据

**全仓库扫描**确认无任何大模型 API 调用：

```

  fetch.py:496          if d in ("cdn.openai.com", "www-cdn.anthropic.com") ...
  extract.py:1358       实测 how-openai-uses-codex.pdf 抽出的文本全是…
```

## 案 2｜「README 引用它才加分」把交付标准抬高一档

### ① 原文（改进前）

README 初稿中，`work/reports/manifest.json` 只是**目录树注释里的一行字**：

```
│   ├── reports/                   manifest.json · fetch_report.json · extract_report.json
```

而核心数字是以「结论」形式直接列出的：

```
| **可翻译正文** | **517,216 字符 / 76,324 英文词**（严格抽取口径） |
```

存在的问题不是数字错了（数字是对的，来自 `manifest.json`），而是：

- **无口径说明**：517,216 是怎么算出来的？「严格口径」意味着什么？
- **无字段出处**：读者无法从 README 反查到 manifest 的具体字段
- **无核验路径**：读者只能选择相信，不能自己验证
- **manifest 的绝大部分价值未被使用**：该文件记录的交叉校验机制、
  逐文档可信度标记、抓取缺口分类，README 一句未提

### ② 你的 prompt

> 「**光有 manifest.json 不加分，README 引用它才加分。**」

这条指令把交付标准从「**文件存在**」提升为「**文件被实际使用**」，
并要求可被引用 —— 即数字必须有出处。

### ③ 产出

README 第 2 节重构，新增两小节：

**2.3「为什么这些数字可信」** —— 把 manifest 真正有价值的部分写出来：

| 内容 | 说明 |
|---|---|
| 双口径同时保留 | 严格 517,216 字符 / 宽松 3,805,381 字符；差异过大即标 `needs_review` 交人工复核，**不在两个数字里默默选一个** |
| 逐文档可信度标记 | `extract_warnings` 33 篇 · `chars_reliable=false` 6 篇 · `garbage_rate>0.10` 11 篇 · `failure_root_cause` 5 篇 |
| 抓取缺口 5 类归因 | `already_archived` 29 · `http_404` 15 · `needs_account` 20 · `not_attempted` 41 · `unreachable_automated` 3，共 108 条 |
| 语义严格区分 | `http_404` 是「确认不存在」，`not_attempted`/`network_error` 是「**未核查**」，两者不可混淆 |

**2.4「怎么复核」** —— 给出 5 条可复制执行的命令（读关键数字、看交叉校验与
`needs_review_ids`、看 108 条缺口分类、看单篇逐项证据），以及 manifest 顶层结构表。

同时 2.2 规模表的表头由「项 / 数值」改为「项 / 数值 / **manifest 字段**」，
每个数字标出对应字段，例如：

```
| 可翻译正文（严格口径） | 517,216 字符 / 76,324 英文词 | summary.reading_translatable_chars |
| 剥壳前全量（宽松口径） | 3,805,381 字符 / 464,510 英文词 | summary.totals.chars_loose   |
| 阅读文章抽取成功       | 27 / 31                      | summary.reading_html_ok       |
```

### ④ 对比（改进前后）

| 项 | 改进前 | 改进后 |
|---|---|---|
| manifest 在 README 中的引用次数 | 1（仅目录树一行） | **17 处** |
| 数字带字段出处 | 0 | **8 个** |
| 可复制执行的复核命令 | 0 | **5 条** |
| 交叉校验机制是否说明 | 未提 | 已说明（含 `needs_review` 触发条件） |
| 逐文档可信度标记是否说明 | 未提 | 已说明（4 类计数） |
| 108 条抓取缺口归因 | 未提 | 已说明（5 类语义区分） |
| 语义口径（确认不存在 vs 未核查） | 未提 | 已明确 |

### ⑤ 证据

- README 章节：`## 2. 来源与覆盖范围` 下的 `### 2.2 / 2.3 / 2.4`
- 数据来源：`work/reports/manifest.json` 的 `summary` / `cross_check` / `thresholds` / `known_gaps`
- 引用密度与字段数经脚本核验：README 中 `manifest` 出现 17 次，
  「manifest 字段」列表头存在，引用的 8 个数字与 manifest 实际值逐项一致

## 案 3｜「我们要的是抽取新术语表」推翻原方案

### ① 原文（我的错误方向）

换源复用议题提出后，我给出的方案是：

> **把 99 条 `CURATED` 术语表从 `init_glossary.py` 抽成独立的 JSON 数据文件**，
> 换源时替换这个文件即可 —— 实现「数据与代码分离」。

这个方案解决的是「**术语表存在哪**」的问题。

但负责人回看后指出，真正的问题不是这个。

### ② 你的 prompt（逐字）

> 「我仔细回看了一下，我们需要的是让换源后有脚本能**抽取**新的术语表，
> 而不是**改正**现在的术语表，你的意见呢」

这句话包含两层信息：

1. **目标重述**：需要的是「从新语料抽取新表」，不是「把现有表挪个位置」
2. **主动征询反对意见**：「你的意见呢」—— 明确邀请我评估，而不是直接下命令

我评估后**认同该判断，并推翻了自己的原方案**。理由是可实测的：
`init_glossary.py` 的自动抽取能力（`candidate_phrases` → `rank_candidates` →
`build_glossary`）一直存在，只是被 `DEFAULT_MAX_TERMS = 0` 关闭。
真正缺失的是「**不带种子、纯从新语料建表**」的模式。

### ③ 产出

`scripts/init_glossary.py` 新增**无种子模式** `--from-corpus-only`（别名 `--no-seed`），
`build_glossary()` 签名扩展：

```python
def build_glossary(docs, top=DEFAULT_TOP, max_terms=DEFAULT_MAX_TERMS,
                   curated=None, proper_names=None):
    if curated is None:
        curated = CURATED            # 默认行为一字不变
    if proper_names is None:
        proper_names = PROPER_NAMES
```

配套三处设计（均写入代码注释）：

| 设计 | 原因 |
|---|---|
| `curated` / `proper_names` 变为参数 | 换到别的领域时，旧领域的定稿术语与专名表对新语料是**假阳性** |
| `frozen` 改为条件性 | 只有含人工定稿术语才 `frozen=True`；纯自动候选产出标 `frozen=false`，如实反映「尚未被人复查」 |
| `--from-corpus-only` 未配 `--max-terms` 直接报错退出 | 无种子 + 上限为 0 会产出空表，没有意义，应当拒绝而非静默 |

### ④ 对比（同一份语料实测）

测试语料：一份与本项目领域无关的文档（水培主题，211 英文词）。

| 模式 | 术语条数 | **零槽位术语** | `frozen` | 术语来源 |
|---|---|---|---|---|
| 默认（带种子） | 99 | **98** | `true` | 99 条全部来自旧领域 CURATED |
| `--from-corpus-only` | 40 | **0** | `false` | 40 条全部来自当前语料 |

**关键数字：零槽位 98 → 0**。零槽位指「术语表里有、但原文中不出现」——
它直接衡量术语表与语料的匹配度。98 条零槽位意味着旧术语表对新语料几乎完全无效。

同时，无种子模式被明确标注为**草稿态**（`frozen=false`），
并如实说明其局限：自动候选会混入跨句碎片（实测如 `reservoir requires careful`），
需人工筛选后再定稿冻结。

### ⑤ 证据

- 代码位置：`scripts/init_glossary.py` 的 `build_glossary()`、
  `--from-corpus-only` 参数解析、`frozen` 条件判定
- 实测输出：两次 `init_glossary.py` 执行的控制台输出（术语条数、零槽位计数、冻结哈希）
- 端到端验证：以 `run_all.py --source-root <新目录> --from-corpus-only --max-terms 40`
  完整跑通 5 步，产出全部落在新目录，主仓库零污染

## 小结

三个案例的共同点：**负责人的介入都发生在方向固化为大量产出之前**，
且都以简短、可判定的表述完成。

| 案例 | 介入形式 | 一句话成本 | 避免的代价 |
|---|---|---|---|
| 案 1 | 给出硬约束 | 6 个字（无密钥无额度） | 整条 API 路线的实现与返工 |
| 案 2 | 划定交付标准 | 一句（README 引用它才加分） | 交付物停留在「文件存在」层面 |
| 案 3 | 重述目标 + 征询意见 | 一句（含「你的意见呢」） | 按错误方向实现并返工 |

其中案 3 值得单独一提：「**你的意见呢**」这个措辞实际触发了方案的推翻。
如果当时是直接指令（「改成从新语料抽表」），方案同样会改，
但**不会产生「原方案错在哪」的分析**——而那部分认识（抽取能力一直存在、
缺的是无种子模式）是后续实现的基础。
