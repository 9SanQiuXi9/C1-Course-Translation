# AAR｜CS146S 课程资料中文翻译项目

**复盘类型**：After Action Review（七维度评估）
**复盘对象**：项目负责人（人类方）在本项目中的决策、指导与把关行为
**协作形式**：人与 AI 助手结对，AI 承担实现与验证，人类承担需求界定、方向裁决与验收
**产出物**：`README.md`、`docs/材料翻译流水线SOP.md`、`docs/AI协作日志.md`，以及 10 个管线脚本与 41 篇译文

---

## 0. 复盘说明

### 0.1 评估范围

本复盘评估**项目负责人**的行为，而非 AI 的表现。AI 相关的内容单列于第 9 节，
用途是帮助判断「哪些环节应当由人来把关」。

### 0.2 证据基础

本复盘只使用可核查的证据，来源限定为：

| 来源 | 说明 |
|---|---|
| 本项目负责人的指令原文 | 协作过程中的即时消息 |
| 代码与产物 | `scripts/` 下 10 个脚本、`work/quality/stats.json` 等 |
| 执行日志 | `work/logs/` 共 121 条 |
| AI 的产出记录 | 提交说明与验证脚本输出 |

**不做的事**：不推测未表达的想法，不评估无法观察的动机，不给无样本支撑的量化分数。

### 0.3 评级口径

采用**定性三级**，不用 1–5 分数：

| 评级 | 含义 |
|---|---|
| **A 优** | 做法可复用，且有可验证的效果 |
| **B 良** | 做法总体有效，存在可改进之处 |
| **C 待改进** | 存在已被观察到、且可具体改进的缺口 |

> 说明：选择定性评级而非数值打分 —— AAR 评估的是人在具体情境下的判断，
> 三级足以区分「可复用」「总体有效」「有明确缺口」三种状态；
> 分辨率再高一档反而会引入主观噪声，不利于据此改进。

### 0.4 七维度总览

| 维度 | 评级 | 一句话结论 |
|---|---|---|
| A1 目标与范围管理 | **A 优** | 三次一句话纠偏即完成方向校准，范围裁决明确 |
| A2 决策与风险判断 | **B 良** | 关键决策前置且果断；风险标注被批准后缺跟踪 |
| A3 指导与工具使用 | **A 优** | 一条架构性约束决定了整体设计 |
| A4 交付前自行把关 | **A 优** | 四次显式设置检查点，均在不可逆产出之前 |
| A5 提示词质量 | **A 优** | 以「约束 + 验收标准 + 反例」为主导范式 |
| A6 交接与文档标准 | **A 优** | 明确区分「文件存在」与「文件被使用」 |
| A7 节奏与投入分配 | **B 良** | 注意力集中度高，但前后分布不均 |

## A1 目标与范围管理

**评级：A 优**

### 观测

项目目标在启动阶段即被界定为「课程资料的获取 → 抽取 → 术语 → 翻译 → 校验全流程，
以及可复现的处理管线」，并在推进中通过三次范围裁决保持可控：

| 时点 | 原话 | 作用 |
|---|---|---|
| 整理阶段 | 「我只是让你整理」 | 将 AI 扩大的改动范围收回 |
| 翻译阶段 | 「不要在去修理术语表什么的，现在只进行翻译」 | 划定阶段边界，停止术语表打磨 |
| 翻译范围 | 「剩余核心课程翻译就行了，其余的不用翻译」 | 明确取舍，最终定为 41 篇而非全量 |

此外还有一次**方向级纠偏**（见 A2），以及一次**停止条件设定**（「我觉得够了」）。

### 归因

这三次纠偏的共同特点是：**只花一句话，且直指范围而非细节**。没有出现
「逐条指出 AI 哪里做错了」的情形 —— 说明负责人对「当前该做什么」有清晰判断，
并能用最少的语言完成校准。

「核心课程优先」的裁决尤其有效：它把「翻译多少篇」这个开放问题转成
「翻译哪一类」这个可判断问题，直接收敛了工作量。

### 建议

**保持**。若用于其他项目，可再补一条显式的停止条件（例如「每阶段产出达到
什么标准即视为完成」），使范围边界不仅有上界，也有下界。

## A2 决策与风险判断

**评级：B 良**

### 观测

**（1）关键决策在动手前完成 —— 效果可验证**

在校验器开发前，负责人要求「请先给出设计方案…我确认后再给完整代码」，
并对方案的 4 个待定问题逐条回应：「1，我同意放在这里 2，不分开 3，允许误差 4，可以」。

这 4 个问题分别涉及输出位置、报告结构、容差策略、采样方式。**每一条若判断不同，
都会导致大段返工**。事先确认把这部分成本前置消纳了。

**（2）决策果断，且不追求完美**

- 换源参数化批准为「好」，未在细节上反复
- 术语候选抽取质量问题在评估后裁决为「我觉得够了」，**主动接受已知不完美**而非无限优化

**（3）方向判断具备自我复核能力**

负责人主动回看后指出：「我们需要的是让换源后有脚本能抽取新的术语表，
而不是改正现在的术语表」，并以「你的意见呢」征询。这次纠偏推翻了 AI 原本的方案
（把术语表抽成独立 JSON 文件），且负责人判断是正确的。

### 归因

**优点**：决策前置、敢于收敛。

**可改进处**：`check_quality.py` 设计确认时，AI 标注了「L4 语义层需人工标注」
这一风险，负责人回应「4，可以」。风险被批准，但**后续未再跟踪**，
最终 L4 未执行。这属于「风险已识别、未纳入跟踪」的常见缺口，而非判断失误。

### 建议

在对方案说「可以」时，**把其中的风险项单独抄进一份待办清单**，
并在阶段结束时回看该清单。具体到本项目，可以是一条：
「L4 需人工标注 `annotator_A/B.json` —— 状态：待办」。

## A3 指导与工具使用

**评级：A 优**

### 观测

**（1）一条约束决定了整体架构**

负责人在布置翻译队列脚本时给出了关键约束：**「无密钥无额度」**。

这一句直接排除了「脚本调用大模型 API」的路线，把设计空间收敛到
「排队 → 生成 prompt → 严格校验 → 落盘 → 留痕 → 进度」的半自动模式。
该模式此后未再改动。

**（2）用流程约束替代事后返工**

「请先给出设计方案…我确认后再给完整代码」是一条**流程性指令**。
它的价值不在单次沟通，而在建立了一个可重复的协作节奏：AI 提交设计 → 人裁决 → AI 实现。

**（3）给出可判定的验收条件**

「在报告里标注"无可译内容"，**而且要标注情况**」—— 后半句把要求从
「打一个标记」提升为「记录原因」，直接产生了空壳分类机制。

### 归因

负责人对 AI 的使用方式体现出两点清晰的判断：

- **约束优于描述**：给出边界条件（不能用 API），比描述期望功能更能收敛设计
- **流程优于检查**：把检查嵌进流程（先设计后实现），比事后逐行审查成本更低

### 建议

**保持**。可复用的一句话模板：**「约束：____；产出物：____；验收标准：____」**。

## A4 交付前自行把关

**评级：A 优**

### 观测

负责人在项目中**至少四次显式设置检查点**，且均位于「即将产生大量不可逆产出」之前：

| # | 时点 | 原话 | 把关效果 |
|---|---|---|---|
| 1 | 校验器开发前 | 「请先给出设计方案…我确认后再给完整代码」 | 消纳 4 个设计分歧 |
| 2 | 管线计划前 | 「你先说一下你准备把什么写到日志里，再动手」 | 避免日志写偏 |
| 3 | 换源方案 | 「我仔细回看了一下…你的意见呢」 | 推翻 AI 原方案 |
| 4 | 本次 AAR | 「先写出你要写的，我过目之后再开始行动」 | 确认七维度框架 |

另有两次轻量介入：「先不用管，先按照图片中的顺序将管线脚本的一键入口做出来」
（明确优先级）、「就按照真实参数就行，但注意不要隐私泄露」（附加质量要求）。

### 归因

**这是有意设计的机制，而非偶然**。四次检查点的分布显示出一致的取向：
**在方向尚未固化为代码/文档之前介入，而不是在成品上做逐行审阅**。

这种取向的收益是可验证的 —— 检查点 1 涉及的 4 个设计问题，任意一条判断不同
都会导致大段返工。

### 建议

**检查点集中在「动手前」，可补一次「交付后」的抽样验收。**

本项目唯一一次发现实质缺陷（校验器自测与生产路径不一致，导致自测失效），
来源是 AI 的自测，而**非负责人的抽查**。当时自测输出的结论是「8/8 通过」，
从外部看是正常的。

低成本的做法：在某一阶段结束时，**随机抽 1–2 个产物亲自看**。例如随机打开
2 篇译文对照英文原文，或要求 AI 现场演示一次「故意注入错误、校验器能否报错」。
这类抽查不需要通读，但能发现「检查机制本身失效」这一类问题。

> 补充说明：本项目负责人对交付内容的关注度实际很高 —— 例如主动追问
> 「我的管线文件夹在哪」、「最重要的翻译脚本呢」、以及对 README 数字来源的
> 追问（「光照 manifest.json 不加分，README 引用它才加分」）。上述建议是
> 「在已有的关注之外，增加一次随机抽样」，而非「关注不足」。

## A5 提示词质量

**评级：A 优**

### 观测

负责人的提示词以**约束与标准**为主导，而非任务描述。按成分归类如下：

| 成分 | 实例 |
|---|---|
| **产出物定义** | 「写一个 Python 脚本，用于校验一个翻译项目的质量」 |
| **架构性硬约束** | 「无密钥无额度」 |
| **流程约束** | 「请先给出设计方案…我确认后再给完整代码」 |
| **验收标准** | 「在报告里标注"无可译内容"，**而且要标注情况**」 |
| **反例/纠偏范式** | 「搜不到 ≠ 不存在」 |
| **结构化回应** | 「1，我同意放在这里 2，不分开 3，允许误差 4，可以」 |
| **范围裁决** | 「剩余核心课程翻译就行了，其余的不用翻译」 |
| **质量门槛** | 「光有 manifest.json 不加分，README 引用它才加分」 |
| **流程纪律** | 「不要在去修理术语表什么的，现在只进行翻译」 |
| **范围声明** | 「这是小问题，先不用管，先按照图片中的顺序…」 |
| **附加要求** | 「就按照真实参数就行，但注意不要隐私泄露」 |

**核心观察**：提示词模式是 **「约束 + 验收标准 + 反例」**，而不是
「请帮我做 X」。其中效果最直接的三条：

1. **「无密钥无额度」** —— 一句话排除了整条技术路线
2. **「搜不到 ≠ 不存在」** —— 给出的是判据范式，可直接落到代码里
3. **「你的意见呢」** —— 明确邀请 AI 提出反对意见，实际触发了方案推翻

### 归因

这类提示词的可执行性明显更高，原因是：
- **约束消歧**：把「要做成什么样」而非「要做什么」说清楚，减少理解偏差
- **标准可判**：验收标准具体到可检查（「标注情况」而非「标注一下」）
- **反例可传**：给出错误范式，比给出正确要求更容易被准确实现

### 建议

**保持**。若用于团队协作，这套提示词结构值得沉淀为模板：

```
背景：____
产出物：____
硬约束：____（如：不可用外部依赖 / 无网络 / 无密钥）
验收标准：____（可检查）
反例：____（什么是错的）
```

**一处可改进**：个别指令存在指代不明确的情况。例如「最重要的翻译脚本呢」——
`translate_queue.py` 确实存在于 `scripts/`，但该表述也可能指「期待一个能直接产出
中文的脚本」，AI 按前一种理解作答，可能未命中真实意图。

建议在提问涉及具体对象时，**直接给出文件名或一句功能描述**，
可进一步降低往返成本。

## A6 交接与文档标准

**评级：A 优**

### 观测

负责人对交付物提出了一条清晰且高于常规的标准：

> 「光有 manifest.json 不加分，README 引用它才加分。」

这条标准把要求从「**文件存在**」提升为「**文件被实际使用**」。其效果可验证：
`manifest.json` 原本只在 README 的目录树里占一行字；调整后，README 的
「为什么这些数字可信」一节建立在 manifest 的口径声明、交叉校验与缺口分类之上，
每个数字都可反查到对应字段。

负责人对交接物的完整性也有明确要求，直接列全了 README 应覆盖的内容：
「来源、覆盖范围、翻译流程、使用方法、已知缺口」，并追加「注意不要隐私泄露」。

### 归因

负责人关注的不是「有没有文档」，而是「**接手的人能不能用**」。这一点在两次
追问中体现得很清楚：「我的管线文件夹在哪」（可用性）、「最重要的翻译脚本呢」
（关键路径是否突出）。

### 建议

**保持这条标准**，并可再补一条**反向检查**：请一位未参与的人按 README
尝试跑通一次，记录卡住的位置。本项目已具备此条件（管线支持 `--source-root`
在独立目录完整运行），验证成本较低。

## A7 节奏与投入分配

**评级：B 良**

### 观测

**（1）纠偏及时，未让偏差累积**

三次范围纠偏均发生在偏差刚出现的阶段，没有出现「大段产出后整体推翻」的情况。
换源方向的纠偏同样如此 —— 在开始实现前完成。

**（2）主动收敛，拒绝无限优化**

术语候选抽取的质量问题（候选混入跨句碎片）被识别后，负责人裁决「我觉得够了」，
并明确接受「草稿 + 人工筛」的定位。这是有意识的取舍。

**（3）注意力分布前重后轻**

两处可观察到的不均衡：

- **术语表环节投入较多轮次**，最终由负责人自己叫停
  （「不要在去修理术语表什么的」）—— 属于自我修正，但成本已发生
- **README 长期未同步**：在翻译已完成 41 篇的情况下，README 仍停留在
  「翻译进度 1 / 57」，直到整体重写时才更新

### 归因

**优点**：纠偏成本控制得好，且能主动止损。

**可改进处**：产出物的**同步节奏**没有和产出节奏绑定。文档被当作「最后写的
东西」，而非「随产出更新的东西」，因此出现了明显的滞后。

### 建议

给关键产出物设定**更新触发条件**，而不是等「有空再改」。例如：

> 翻译进度每增加 10 篇 → 更新 README 的进度数字

本项目 README 中**其他**数字都能从脚本反查（这一点做得很好），
唯独进度类数字需要人工同步 —— 它恰恰就是滞后的那部分。可考虑把进度数字
也改为「引用 `_progress.json`」而非手写，从机制上消除滞后。

## 8. 结论

### 8.1 可复用的做法清单

本项目验证有效的做法，建议固化为个人/团队习惯：

| # | 做法 | 证据 |
|---|---|---|
| 1 | **先要设计方案，确认后再要代码** | 消纳 4 个设计分歧，避免大段返工 |
| 2 | **给架构性硬约束，而非功能描述** | 「无密钥无额度」一句话定路线 |
| 3 | **纠偏只说范围，不逐条纠错** | 三次均为一句话完成校准 |
| 4 | **验收标准具体到可检查** | 「而且要标注情况」产生了分类机制 |
| 5 | **用反例传递判据** | 「搜不到 ≠ 不存在」 |
| 6 | **明确邀请反对意见** | 「你的意见呢」触发方案推翻 |
| 7 | **交付物标准是「被使用」而非「存在」** | 「README 引用它才加分」 |
| 8 | **在合适时机接受不完美** | 「我觉得够了」 |

### 8.2 建议改进项

| # | 改进项 | 触发场景 | 可检查的完成标准 |
|---|---|---|---|
| 1 | 交付后增加一次**随机抽样验收** | 每阶段结束 | 随机看 2 个产物，或要求演示一次「注入错误能否报错」 |
| 2 | 获批的风险项抄入**待办跟踪** | 对方案说「可以」时 | 待办清单存在且被回看（如 L4 标注） |
| 3 | 关键产出物设**更新触发条件** | 产出持续推进时 | 进度类数字改为引用 `_progress.json`，非手写 |
| 4 | 涉及具体对象时**给出文件名或功能描述** | 提问时 | 减少一轮澄清往返 |
| 5 | 为阶段补一条**显式的完成定义** | 阶段启动时 | 每阶段有一条「什么算完成」 |

> 第 1 项与第 4 项优先级最高：前者针对「检查机制本身可能失效」这一系统性风险，
> 后者成本极低、收益即时。

## 9. 附：协作对方（AI）的能力边界

本节供判断「哪些环节应当由人把关」。内容全部来自本项目中被实际观察到的情况。

### 9.1 已验证可靠的方面

- 按明确约束实现（「无密钥无额度」下未尝试网络调用）
- 主动自测并如实报告失败（L3 反例自测 8/8、`fetch` 自测 5 个场景）
- 自我纠错后如实记录（临时脚本带断言、改完复查、用后即删）

### 9.2 已观察到需要人把关的方面

| # | 情况 | 本项目实例 |
|---|---|---|
| 1 | **判定逻辑可能「看似通过」** | 自测与生产走两条路径，导致自测永远显示通过；发现者是自测本身而非抽查 |
| 2 | **方向判断可能出错，需人复核** | 原方案「把术语表抽成独立 JSON」被判定为方向错误；由负责人主动回看后纠正 |
| 3 | **「顺手做的小事」失误率高于主线** | 常量区误改默认值、文档示例用了 PowerShell 不支持的续行符、核验脚本自身逻辑错误等，本项目中记录约 10 处 |
| 4 | **注意力易集中于单点** | 在术语表环节持续打磨，直至被负责人叫停 |
| 5 | **表述可能未命中真实意图** | 对「最重要的翻译脚本呢」按字面理解作答，未确认是否另有期待 |

### 9.3 由此得到的协作原则

1. **结构性改动前要设计**（成本最低的把关）
2. **校验机制本身需要被校验**（例如要求演示「注入错误能否报错」）
3. **方向类判断由人复核**（AI 可能在某条路上走得很深却是错的方向）
4. **小事不要省审阅**（失误集中在此）
5. **对关键产出物设定同步机制**，而非依赖事后补记
