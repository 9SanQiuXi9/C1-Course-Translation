#### 原型是新规格，而规格是新的……源代码？

在我的职业生涯里，规格说明越来越短。我刚进 Microsoft 时，衡量一位 PM 价值的标准是规格说明有多厚。多年后，在 Tripadvisor，我们把那位拿着一张餐巾纸上草草写就的规格来参加产品评审的 PM 奉为传奇。

产品团队常常把规格说明当成文书工作 —— 在真正「干活」交付之前必须忍受的麻烦。工程师因优雅的代码被称赞，设计师因漂亮的用户体验被称赞，PM 因交付影响力而获赞。但规格说明呢？它们通常被草草带过、丢到一边、被人遗忘。

感谢阅读 Ravi on Product！免费订阅即可收到新文章并支持我的工作。

订阅

这一直是个错误。在我的

[《产品能力工具箱》里，「功能规格说明」之所以高居首位 —— 在十二项能力中排第一 —— 是有原因的。它支撑着产品执行，与产品交付、产品质量并列。](https://www.ravi-mehta.com/product-manager-skills/)

无懈可击的执行是优秀产品管理的基础，而一份出色的规格说明就是起跑线。

今天，我们构建产品的方式正在改变。工程师变快了 —— 快得多。AI 能在几分钟内把粗略的想法变成可运行的代码。瓶颈不再是构建，而是知道要构建什么，并让团队围绕这些需求达成一致。

忽然之间，那份不起眼的规格说明不再是转瞬即逝的文书工作。它成了产品管理的基石 —— 它正在变成源代码本身。

为什么 PM 突然成了瓶颈

在他近期的演讲

[《用 AI 更快地构建》中，吴恩达指出了一个前所未有的趋势：](https://www.youtube.com/watch?v=RNJCfif1dPY)

「这是我有生以来第一次看到有管理者向我提议，让 PM 的数量达到工程师的两倍。我仍然不知道这个提议是不是好主意，但我认为它标志着世界正在往哪个方向走。」——吴恩达

这印证了我们在

[上一篇文章中的预测：随着工程师借助 AI 交付速度快上许多倍，公司需要更多 PM 来支撑这些高产的工程师，而不是更少。](https://blog.ravi-mehta.com/p/will-ai-kill-product-management)

随着产品交付加速，产品管理其他每一个方面都承受着巨大压力 —— 理解客户需求、打造正确的功能、验证影响力。

而所有这些压力最终都会聚焦到一件产物上 —— 规格说明。

规格说明 —— 新的源代码

在传统软件开发中，程序员编写人类可读的「源代码」，它会被编译成高度优化、机器可读的「目标代码」。「目标代码」（也称二进制）是副产品，可以用源代码重新生成。源代码才是名副其实的事实来源。

来自 OpenAI 的 Sean Grove 有一个颇具挑衅性的论点。在他近期的演讲

[《新的代码》中，他主张一份写得好提示词（也就是规格说明）才是新的源代码。](https://www.youtube.com/watch?v=8rABwKRsec4)

从这个角度看，我们做 AI 开发的方式是反的。我们精心编写提示词，向模型传达我们的意图。AI 生成代码。然后我们保留代码，把提示词丢掉。

「这感觉就像是，你把源文件碎掉，然后非常仔细地对二进制做版本控制，」Grove 如此观察。

想想这一点。在传统编程中，源代码是神圣的。源文件包含注释、结构以及文档 —— 理解并修改这个系统所需的一切。二进制只是一个下游产物。

但在 AI 时代，我们把这个关系颠倒了。我们把生成的代码当成值得保留的产物，而把规格说明 —— 也就是提示词 —— 当成用完即弃的东西。

Grove 认为这恰好搞反了。代码，即使是优雅的代码，也是他所说的对规格说明的「有损投影」。就像反编译二进制不会还给你原本的注释与变量名一样，读代码也无法告诉你它背后的全部意图。

而规格说明包含一切。一份足够健壮的规格说明可以生成「优秀的 TypeScript、优秀的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客」。

「一份足够健壮的规格说明可以生成优秀的 TypeScript、优秀的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客。」——Sean Grove，OpenAI

更重要的是，规格说明能做到代码做不到的事：它让人类与机器在共同目标上达成一致。Grove 说得直白：「一份写下来的规格说明能有效地让人达成一致，它是你用来沟通、讨论、辩论、引用并同步的产物。」

他预测：「在不久的将来，沟通最有效的人就是最有价值的程序员。而且说白了，只要你能有效沟通，你就能编程。」

新的稀缺技能不是写代码，而是写出能完整承载意图与价值的规格说明。

对产品经理来说，这听着应该很熟。这正是我们一直在做的事 —— 只不过现在机器也在听。

等等，不是原型杀死了规格说明吗？

直到最近，产品生命周期都必须从规格说明（或 PRD、概念文档、餐巾纸）开始，由它启动最初的线框图、设计、原型与 MVP 开发。

传统做法感觉像是必须忍受的麻烦。工程师先做出基础 MVP，把某样东西 —— 任何东西 —— 送到客户手里。「如果你对产品的第一版不感到难堪，说明你发布得太晚了」成了信条。

我们构建产品的整个方式最近经历了重大转变，而在这个新世界里，规格说明往往是产出，而不是输入。

今天，你不需要交付一行代码就能把原型送到客户手里。v0、Lovable、Replit 这类工具让你能在几小时而不是几周内搭出可用的原型。无需工程介入。

这不只是更快 —— 而是根本不同。手握一个「凭感觉写出来（vibe code）」的原型，你可以在写下功能规格说明的第一行之前，就收集到真实的客户反馈。你可以检验假设、迭代流程、打磨交互。

- 旧工作流是这样：模糊想法 → 线框图 → 设计 → 工程师构建 MVP → 客户反馈 → 痛苦地修订规格 → 线框图 → 设计 → 重建 → 祈祷。

- 新工作流：模糊想法 → 快速原型 → 客户反馈 → 无比清晰的规格说明 → AI 辅助的实现。

原型没有杀死规格说明，它们让规格说明变得更好。

交给 Danny……

以下是我最近做的一个例子。作为背景，我们在构建一个产品，让专家级的影响者把自己网络里的候选人送进工作岗位。上线一个新的落地页之后，我们需要给专家们一个快捷方式，去访问属于他们自己页面的链接。

我们需要在页头放一个按钮，跳转到 company-apply 页面。我目前专注于邮件这块。如果你能接手，这个是可以凭感觉写代码搞定的。

这是我联合创始人发来的消息，说的是一个需要上线的小按钮。足够简单，而且恰恰是如今非技术人员可以自己交付的那类事情。

以下是它在几分钟内上线的配置与步骤：

- 项目管理工具：
- [Linear](https://linear.app/homepage)

- IDE：
- [VS Code](https://code.visualstudio.com/)

- 扩展：
- [GitHub Copilot Pro](https://code.visualstudio.com/docs/copilot/overview)

- 模型：
- [Claude Sonnet 4](https://claude.ai/login?returnTo=/?)

- MCP 服务器：
- [Linear MCP 服务器，让 Linear 工单可以通过 Copilot 访问](https://linear.app/changelog/2025-05-01-mcp)

我们来看一下流程中的步骤（可对着上面的 Loom 视频跟做）：

1. 从我联合创始人的 Slack 消息生成一个 Linear 工单（00:14）

2. 在上面的工单里澄清我希望新文案写成什么样（00:25）

3. 打开 Copilot，提示 Claude 打开该 Linear 工单（01:18）

4. 提示 Claude 审查该工单，并相对于代码库分析它（01:52）

5. 提示 Claude 创建一个分支并实现这些改动（02:30）

6. 测试改动，确认它们按预期工作。（02:52）

7. 在 GitHub 上开一个拉取请求（PR），把这些改动合入代码库（03:55）

8. 等一位工程师审查/批准该 PR

把视角拉远，这套配置真正的威力就清晰了。是的，这是个微不足道的例子，但要点依然成立：一个非技术人员现在可以在 Linear 工单、代码库与工程师之间来回穿梭，全靠通过 GitHub Copilot 给 Claude 的几句提示。

而且再次强调，这一切的关键部分不是代码本身，而是规格说明。

现在，有必要对上述做法加上几条前提，说明它要良好运作需要什么：

1. 要具体：用模糊的规格只会得到一个混乱的代码库。用 Claude 拿工单初稿去对照代码库、帮助写得更具体，是这个流程中不可或缺的一环。在我们这里，我们还另有一份「如何写好规格说明」的准则。

2. 要有选择：上述做法最适用于较简单的任务。工单越复杂，就越需要懂行的人参与（在这些情况下，「自助」到头来根本不是自助）。

3. 要有把关：这种做法之所以行之有效，正是因为有真正的工程师懂行，负责审查改动，并确保简洁与功能之间的平衡得以维持。

但要说清楚：规则已经变了。对每一个构建产品的人来说 —— 包括 LLM —— 规格说明都是事实来源。

有了正确的配置，作为非技术人员为代码库做贡献是完全现实的预期。只要有足够的时间与耐心，你可以开始理解代码库并自己实现改动，而不是每次都只靠 Claude 来救场。

有一天，你甚至可能一边喝着咖啡，一边让 AI 智能体把你的工单交付上线。

如果你是 PM，正在担心 AI 会对你的工作做什么，关键在于认识到这份工作本身在变。但其他人也一样。好的一面是，一位优秀 PM 所需的核心技能在这个新世界里反而更有价值。

规格说明万岁！

创造了「赛博空间」一词的科幻作家 William Gibson 曾说：

未来已经到来 —— 只是分布得还很不均匀。

当我思考 AI 能做什么、不能做什么时，就会想起这句话。今天，AI 带来的收益极不均匀。有些事情 —— 生成代码、文本、图像 —— 已经实现了量子跃迁，以 AI 的速度运转。另一些事情 —— 与客户交谈、发现他们的需求、说服他们购买 —— 仍然以人的速度推进。

这种不均匀的分布正在重塑产品团队。聚光灯正从实现工作转向理解工作。那些一直让最优秀的 PM 脱颖而出的核心技能 —— 理解用户需求、清晰定义问题、设计优雅方案 —— 已经变得成倍地更有价值。

最优秀的 PM 会把这些洞见变成规格说明 —— 那种能让团队对齐、指导实现，并在日益自动化的开发世界里充当持久产物的规格说明。
