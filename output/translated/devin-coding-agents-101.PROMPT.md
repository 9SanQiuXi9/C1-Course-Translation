开发者工具一直在快速演进。十年前是自动补全与智能提示，能建议方法名并执行程序化重构。四年前是编程助手与 Tab 补全，能替你写出接下来几行代码。两年前是生成式聊天机器人，能协助你开发并为你生成整个文件。而今天，是自主智能体 —— 能把最初的描述一路推进到最终的拉取请求，几乎无需人工干预。过去两年，我们专注于通过构建 Devin 来实现这一愿景。如今，人们对自主智能体的兴趣正达到新的高度，尤其是随着近期类似产品的发布 [1] 除 Devin 之外，近期发布的产品还包括 OpenAI 的 Codex 与 Google 的 Jules。像 Cursor、Claude Code 这类本地智能体可以在并行工作区中运行，从而复现类似的效果。这些智能体可以以多种形态出现，包括 Web 应用、移动应用，以及集成进 Slack、GitHub、Linear、Jira 等常用工具。

虽然人类配合 AI 助手能比任何单独的 AI 完成更多，但自主智能体端到端处理任务的能力带来了全新层次的多任务并行 —— 让每位工程师都变成工程管理者。

适应与这些新 AI 同事高效协作需要一些时间。有意思的是，我们观察到资深到 Staff 级别的工程师往往最快上手并熟练掌握这些工具。最终，这些工具会在所有级别的工程工作中普及。基于我们的经验与客户反馈，我们希望分享一些关键洞见与经验教训，帮助大家把这些工具成功融入工作流。

# 说清你希望怎么做，而不只是做什么

把智能体当成一位决策可能不太可靠的初级编程伙伴。简单任务可以直接描述；但对更复杂的任务，要从一开始就清楚说明你偏好的做法。事先把整体架构与逻辑告诉智能体，不仅能提高它的成功率，也能减少你审查代码的时间 —— 因为你本来就熟悉预期的方法。

### 示例：

与其只说「加单元测试」，不如指明要测的功能、标出重要的边界情况，并说明哪些需要 mock（如果需要的话）。

## 告诉智能体从哪里开始

想一想如果是你自己处理这个任务，你会从哪里入手。即使你不知道具体的文件或函数名，也请提到相关仓库、相关文档以及涉及的关键组件。清楚标出这些要素，能最大限度减少无效劳动与困惑。

### 示例：

「请为我们的代码加上对 Google 模型的支持。你应该看[这里](link)的最新文档，并在模型分组目录里新建一个实现文件」

## 练习防御性提示

想象一下把同样的提示交给一位新来的实习生。哪里最可能出现困惑或错误？预先想到这些点，并主动把指令说清楚，避免歧义。

### 示例：

「请修复我们搜索模块的 C++ 绑定，让新的单元测试通过。注意，你可能每次改完代码都要重新编译绑定，然后再测试。」

## 给它 CI、测试、类型定义与 linter 的权限

智能体的神奇之处很大程度上来自它能修正自己的错误、并依据报错信息迭代。通过类型检查器、linter、单元测试等工具提供强有力的反馈回路，能大幅提升它的表现。考虑用带类型的 Python 而不是普通 Python，或用 TypeScript 而不是 JavaScript。教会你的智能体如何运行常用检查与测试，确保它拥有所有必要的依赖包与访问权限。如果智能体能操作浏览器，请给出运行你前端开发环境的清晰说明。

### 示例：

我们团队从基本无类型的 Python SDK 转向了全部带类型的 SDK（这本身也是一个很适合交给编码智能体的任务）。

## 发挥你自己的专长

当你熟悉自己的代码库时，上面这一切都会变得更容易。即使是简单任务，你验证逻辑与结果的能力也很有价值。人的监督仍然不可或缺 —— 归根结底，代码最终是否正确由你负责。即使这些工具变得越来越精密，所有权与验证仍将是人类工程师的关键职责。

## 立刻接手新任务

想象一位同事给你发消息：「嘿，我们能快速做个 X 吗？」或「我们需要调整一下 Y。」与其让它打断你的思路，不如直接把一条简短提示丢给自主智能体去调查或改动。这样你就能继续专注于手头的主要任务。有个有意思的副项目想法？需要快速做个原型、抓点数据，或复现某篇研究？交给你的智能体，稍后再回来处理。

### 示例：

很多团队在 Slack 上讨论缺陷修复或小功能更新时，就直接 @Devin。

### 示例：

这种灵活性让我们团队在乘车和飞行途中的效率大大提高。

## 把你的杂活交出去

卡在二分查找旧提交上？还是忙着为新功能更新文档？把这些重复性任务交给你的智能体。你会省下宝贵时间，继续专注于更有创造性、更有影响力的事。

### 示例：

在我们团队，工程师交付一个改动后，让智能体去更新所有相关文档与面向用户的文案，是很常见的做法。

## 跳过分析瘫痪

拿不定某个重构是否真能简化你的代码？在两种架构方案之间无法取舍？让你的智能体把两个方案都实现出来。有了具体例子可以比较，决策就变得简单，而且否掉一个方案也不会伤到谁的感情。

把你的 CI/CD 流水线设置为每次新 PR 都自动创建预览部署，给你一个即刻可访问的线上 URL。这在审查 AI 智能体完成的前端任务时尤其方便。

随着你拉取请求的规模与复杂度超出几个文件，一次性处理它们就会变得困难。然而，真正掌握如何委派中大型任务（通常 1-6 小时的工作量），才是自主智能体带来最高投资回报的地方。你省下的不只是几分钟，而是能收回数小时的生产力。较小的任务也许轻松就能搞定，但把智能体的能力拉伸到处理更大的任务，才会带来最大的回报。

## 自动化你的初稿

对于较大的任务，用自主智能体创建 PR 的初稿可以启动进展，并大幅削减你的工作量。这里能否成功，取决于你是否在一开始就清楚传达期望的做法。把自己当成指导初级开发者的架构师。清晰、详细的指令能避免把时间浪费在纠正智能体代码里的根本误解上。

| 领域 | 起草 | 精修 |
| --- | --- | --- |
| 新闻业 | 记者收集初步信息，写出文章初稿 | 编辑审阅草稿、核查事实、润色，并定稿付印。 |
| 餐饮业 | 流水线厨师准备食材，做出初步菜品。 | 副主厨添加调味、调整菜品口味，然后才送到客人桌上。 |
| 编程 | 自主智能体依据初步计划开工，产出第一版解决方案 | 人类开发者审阅草稿 PR、给出反馈，并在合并前做手动精修 |

🛑 请记住，大型任务（目前）还不是完全放手不管的。对于更具挑战性的任务，预期会有多轮反馈循环，也要预期还需要一些手动精修来打磨。现实的目标大约是节省 80% 的时间，而不是完全自动化 —— 你的专业判断在验证与最终质量把关上仍然至关重要。

## 与它共同编写 PRD

对于复杂或定义模糊的任务，与你的自主智能体协作产出一份详细计划会非常有效。你一开始不清楚每个细节或需求是完全正常的。可以先让智能体去探索一些发现性问题，比如「我们的认证系统是怎么工作的？」或「哪些服务可能受影响？」你也可以让智能体指出具体的相关代码位置，供你尽早确认。

某些智能体（例如 Devin 与 Claude Code）提供专门的规划模式，专注于阅读和探索现有代码，而不是立刻修改它。如果你希望在委派任务前做更充分的准备，像

[deepwiki.com 与 Devin Search 这类专门的代码库检索工具，能快速给出关于你代码库的洞见，帮助简化这一过程。](http://deepwiki.com)

## 设置检查点

对于多阶段任务，尤其是涉及多个代码库的，要在过程中设立清晰的检查点：

计划 → 实现一个分块 → 测试 → 修复 → 检查点复核 → 下一个分块

在每个重要阶段后明确要求暂停，特别是对于跨多层（如数据库、后端、前端）构建的复杂功能。用这些检查点来确保实现符合你的预期、澄清疑问（例如「解释一下认证流程并确认它的安全性」），并尽早纠正方向，避免问题层层累积。

### 示例：

「我想让你实现这个功能，它会跨越我们的数据库、后端和多个前端界面。请先规划所需的数据库 schema 变更，完成后告诉我，我好应用迁移。」→「现在请实现后端改动并加上测试，确保 XYZ 能正常工作。完成后告诉我」→「现在在 Web 和移动端两个界面里实现改动，去调用新的后端端点」

[加入智能体的知识库）。](#customization-3)

## 智能代码审查与规则强制执行

虽然已有做快速代码审查的专用工具 [3] 例如 Greptile 与 CodeRabbit，但自主智能体可以是一个有意思的选项，能给出更准确的洞见 —— 尤其是当它们已经索引过你仓库的功能时。

### 示例：

## 接入故障事件与告警

你也可以设置自主智能体，让它们针对特定事件自动触发。例如，Devin 提供易用的 API，其他智能体也可以通过 CLI 命令集成进自定义工作流。这类设置与 MCP 配合使用效果尤佳，可用于摄取第三方错误日志。

⚠️ 在生产服务的故障分诊上，AI 的调试能力并不算强。与其让 AI 端到端修复冒出来的缺陷，更实际的做法往往是让 AI 只标出最可疑的错误、变更等。

## 环境配置

没有什么比不完整或不匹配的环境更拖慢智能体了。为了让一切顺畅运行，把智能体的环境配置与团队保持完全一致。这包括语言版本、依赖包与自动化检查。例如，智能体环境中应安装 pre-commit，而环境配置（密钥、语言版本、虚拟环境、浏览器登录）应通过 .envrc 之类的工具或自定义 .bashrc 配置自动加载。

MCP 已经广泛可用，接入你的智能体与外部工具既快速又便于试验 [4] 在 Devin 中，MCP 仍处于 beta，我们正在探索支持它们的最佳方式。如需访问请联系我们！。但很多人忽视了为智能体编写简单的 CLI 脚本。举个简单的例子，你可以给智能体一个脚本，让它根据票据 ID 拉取 Linear 工单的信息。你也可以给智能体一个工具，用来可靠地完成工作流中的常见环节，比如一个重启本地开发环境的脚本。

## 加入智能体的知识库

如果你的智能体犯了某些常见错误，这正是把反馈固化成智能体知识的时机。Devin 里有专门的知识管理系统。许多产品提供 .rules 文件或 .md 文件供智能体永久摄取。不要只给它关于你所用框架的规范，还要告诉它你项目的整体架构。告诉它不同任务通常用哪种测试、如何运行重要命令，以及你推荐使用哪些工具。

### 示例：

我们把「新增服务路由时应遵循的具体流程」写入智能体的知识。这些信息涵盖它需要在前端与后端添加样板代码的每一个位置。结果，这类任务现在可以轻松委派给我们的 AI。

## 调试能力有限

缺陷报告可能看似简单。但许多缺陷往往不仅需要访问数据库与日志，还需要超出当今多数 AI 智能体水平的调试能力。如果用 AI 辅助调试，我们建议让它给出可能的根因清单，而不是让它自己去调试并修复一切。然后由人根据自己的经验判断哪个才是真正的根因。但一旦确定了原因，智能体在实施修复上仍能帮上不少忙。

## 细粒度视觉推理能力差

总体而言，当今模型在还原设计截图或 Figma 稿所需的细节层面上，视觉推理能力并不好。它们在能用代码描述的视觉内容上最可靠（例如给它 Figma 导出的代码）。如果你希望它匹配你的视觉风格，就应该使用带可复用组件的良好设计系统。

## 知识截止

每当你要使用一个新库时，都应明确把最新文档指给它。否则，由于预训练基础模型的知识截止，多数智能体会沿用这些库的旧模式。只要你把文档指给它，好的智能体就能克服这一点，但你必须留意这件事（记住，智能体甚至不知道这些库有新版）。

## 愿意更早止损

刚接触智能体的人常犯的一个错误是：即使智能体的工作已经偏离方向，也坚持要把这次交互做成功。如果你发现自己想「它在无视我的指令」或「这东西在原地打转」，那就应该果断终止这次对话或手动接手。继续发更多消息，更可能说明你任务本身的内在复杂度超出了智能体的能力，而不是某个能简单纠正的小失误。

## 让实验多样化

如果你是刚上手智能体，我们建议一开始就分散下注。尝试各种不同的提示词与思路。对智能体天然表现好的任务类型加倍投入，对表现不好的及时止损。不必强求每次都必须成功。

## 没有进展时就重新开始

在智能体身上，「重来一次」是正确的选择，而且比在人身上频繁得多。如果你给智能体派了任务，而它在应对反馈或纠正方向上很吃力，那么用一个新智能体重开、把全部指令一次性给足，往往能更快成功。智能体修正一个被搞乱的环境的能力，远不如它从零写新代码的能力。

## 为你的智能体创建账号

一次性邮箱有助于安全地测试各类网站。如果你的智能体需要访问云资源，为它创建自定义 IAM 角色。

## 给它一个开发/预发环境

理想情况下，智能体使用与你团队工程师相同的测试配置。我们建议完全不要给它生产服务的访问权限。使用远程智能体时，你可以在它的远程机器上运行完全隔离的测试环境。

## 只读 API key
