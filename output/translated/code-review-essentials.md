## 软件团队的代码审查要点

09 Feb 2015

代码审查是任何协作式软件项目中不可或缺的一环。大型软件系统通常由不止一个人编写，因此一个高效运转的软件团队需要一套健壮的流程，让成员以及代码库本身都朝着正确的方向前进。

代码审查是一件强大的工具，它能够：

1. 帮助团队成员在系统不断变化时更新自己的心智模型
2. 确保改动确实解决了问题
3. 为设计优缺点打开讨论空间
4. 在缺陷进入生产环境之前就抓住它们
5. 保持代码风格与组织结构的一致性

把这些收益看作一个需求层次是很有帮助的。

![代码审查：需求层次](/images/code_review_hierarchy.png)

## 让团队成员步调一致

代码审查最关键的作用，是让团队每一位成员都朝正确的方向前进。你无法安全地修改一个自己不理解的系统，因此代码审查让整个团队在认知上保持对齐。当 Bob 为账务子系统提交一个拉取请求时，Amy 在审查 Bob 代码的过程中，就更新了自己对该系统的心智模型。Amy 有机会就她看不懂的部分提问，Bob 则既能借机厘清自己的设计决策，也在向别人讲解自己的工作。一个月后当 Amy 需要改动账务子系统时，她的心智模型已经是最新的、随时可用。她花更少时间读代码、在脑子里拼凑系统，而把更多时间用于思考更高层的抽象与设计。每个人都受益，因为每个人都在同一条线上。

## 做好一个拉取请求

在你写下任何一行改动系统的代码之前，先问自己以下问题：

- 「这是我该做的那件事吗？」来自客户、团队内部成员以及其他各方
 的需求总会互相竞争。在深入之前，这是把优先级理清的好办法。迭代／
 冲刺规划会议等其他流程也有助于让它保持在正轨上。
- 「团队已经认同这个改动是对的吗？」如果没有，最好先通过邮件或当面
 发起一次设计讨论。当人们在设计上先达成一致时，你的改动更可能被接受。
- 「我怎样才能把这个改动拆成容易审查、容易理解的
 小块？」小的改动更容易思考与理解。良好的讨论源于团队能够
 快速理解你的改动。如果你的改动极其庞大，
 同事的眼睛会发直，你可能只会收到几条风格上的吹毛求疵。
- 「我要如何测试这个改动，以消灭缺陷并确保正确性？」你可能有
 QA 部门，但交付高质量、可工作的软件仍然是开发者你自己的
 职责。容易被测试的软件通常耦合更松、被拆成更小的
 块、也更容易推理。你必须为所有改动都准备测试方案。

我发现，提前回答这些问题能省下很多长远的头疼。你最不想发生的事，就是花几天写完一个改动，结果它因为根本性的设计缺陷或团队分歧被拒。或者你的改动因为没有人能验证其正确性而被搁置。再次强调，目标是既改动系统，又让其他团队成员跟上你的改动。问自己打算如何把工作拆成一口大小的块并测试这些块，在很多方面都有帮助：

- 它降低风险
- 它让改动更容易推理
- 它推动你走向更好的设计

你宁愿用手术刀做许多小而精确的切口，也不愿用砍刀来一道巨大的伤口。在大多数增量场景下，我更喜欢手术刀驱动的开发，而把砍刀留给该成块删除死代码的时候。

## 发送拉取请求

好，你已经获得团队对你改动的认可，也实现了你一开始想达成的设计。那么实际发送拉取请求最有效的方式是什么？你为这些改动辛苦了很久，希望团队其他成员关注你的拉取请求并快速给出反馈。你该怎么做？

还记得我前面说过，代码审查最重要的部分是让团队共同的心智模型保持良好对齐吗？你的其他同事很可能正在做和你完全不同的工作，也许在系统的完全不同部分。他们的大脑处在完全不同的上下文里，所以你必须通过提供他们做审查所需的指引来克服这一点。这意味着要写一份组织良好的描述，说明你做了哪些改动、为什么这么做，以及任何他们仅靠读代码得不到的相关信息。不要让你的同事做超出必要的脑力劳动。

我们来看一些拉取请求描述的好例子与坏例子：

坏例子：

<!-- CODE_BLOCK_START id=c1 lang= -->
```
Title: Fix uninitialized memory bug
Description:

This is the bug Bob and I talked about earlier. I had
trouble with the compiler but managed to make this work. Let me
know what you guys think.
```
<!-- CODE_BLOCK_END id=c1 -->

如果你是这份拉取请求的开发者，请停下来，设身处地站在审查者的角度想一下。标题含糊，引出的问题比答案还多：内存缺陷在哪里？这个改动有多关键？你和 Bob 之前讨论的是哪个缺陷？你在编译器上遇到什么麻烦？描述既没有提供关于问题的有用上下文，也没有对改动给出有用的说明。如果这份拉取请求很长，审查者只能一头扎进代码，做一番脑力体操试图获得上下文，才刚有机会去思考这个改动如何融入系统连贯的设计。

下面是一个改进过的例子，有助于把改动集讲清楚：

<!-- CODE_BLOCK_START id=c2 lang= -->
```
Title: Fix process crash on startup from uninitialized memory [#54633]
Description:

This bug was causing process crashes on boot due to a memory
initialization error in our statistics Counter class. I talked this
over with Bob, and we both agree the crashes are a rare edge case
that don't warrant a hot-fix release. Here's a summary of the
changes:

  - Moved the underlying int variable into the class initializer
    to prevent ununitialized memory in the Counter.
  - Reworked the Counter interface to simplify caller conditional
    logic and prevent further off-by-one counting problems.
  - Added a unit test that exposes the crash

Testing: I've verified the test suite still passes, and verified
manually that the crash doesn't happen locally.
```
<!-- CODE_BLOCK_END id=c2 -->

这份拉取请求描述在几个方面有所改进：标题足够描述性，给审查者一点简短的上下文，也吸引他们点开邮件了解更多。审查者知道这是进程崩溃（通常是很糟糕的事），并且还有一个缺陷报告编号，如果审查者想进一步了解问题，可以读到关于该缺陷报告的更多细节。新描述还大致指出了问题发生的位置，并有助于交代这个修复有多关键。其中有一段摘要列出了拉取请求中高层的结构性改动，让审查者在看代码之前就在脑中形成改动图景。代码审查者不应该被他们发现的东西吓一跳。这个例子还列出了所执行的测试，这会让审查者相信这些改动经过深思熟虑、经过良好测试、可以合并了。让审查者「点合并」变得傻瓜般容易，为他们的成功铺路。

## 审查者：给出建设性反馈

审查流程的下一个环节，是给同伴建设性的反馈。如果目标是清晰与对齐，那么给出高质量的、建设性的反馈，能帮助每个人更好地理解系统，并推动代码变得更好。

避免说这样的话：

- 「这个设计是坏的。」为什么坏？怎样才能改得
 更好？这类说法打击信心，还可能伤到自尊。
- 「我不喜欢这个改动。」你为什么不喜欢？你希望
 改成什么样？不喜欢某样东西是正常的，但你应该
 把想法讲清楚，并提供关于代码如何改进的有用线索。
- 「你能把它重写得更清楚些吗？」我现在这个有什么问题？
 我该怎么重写？哪里不清楚？这样的评论本身就不清楚，
 也没有给出简单的改进方向。

而要这样说：

- 「这段代码如何处理负整数？」这条反馈很具体，
 并促使开发者自己去想清楚结果。作为审查者，你也许
 知道这段代码遇到负整数会崩溃，但让开发者自己领悟
 更好。这类问题也可能说明测试有缺口，或者需要
 进一步明确范围。
- 「这一段让我困惑，我不明白为什么类 A 要和类 B 通信」如果开发者没有提供有用的
 描述，代码结构也不清晰，这种评论有助于推动设计的清晰化
 与代码的整洁。
- 「看起来你在这里破坏了接口边界。这会对用户产生什么
 影响？」你指出了你注意到的问题，同时给了对方
 善意推定，认为他是有意为之。现在他可以思考破坏接口边界
 那些看不见的后果，要么为自己的决定给出理由，
 要么选择改掉它。

总体而言，把反馈组织成问题的形式，是推动清晰与正确的好办法，同时也帮助开发者在未来改进自己的设计。这通常也是高质量创意写作小组互相给反馈的方式。在创意写作的场景里，说「我不喜欢这个角色」是有害的；而同样的话可以更清楚地重新表述为：「在第一章里你的角色温暖而富有同情心，现在他却冷漠如冰。他看起来不像一个真实的人。」这样就有了具体的、可以用来澄清并找出问题的反馈。

程序员喜欢解决问题、指出毛病，所以他们天性上喜欢发现并指出缺陷。把代码审查看成证明自己聪明、能在同伴代码里找出问题的机会，是很诱人的。别这么做。代码审查是让更多双眼睛看同一个改动、找出关键问题的方式，但你的目标应该是以一种鼓励团队成员在解决问题的同时提升技能的方式来审查。

## 关于风格的点

大括号位置、变量／函数命名、缩进与空格问题都应该处理，但它们不是好的代码审查的核心目的（注意我把它们放在了代码审查金字塔的顶端）。如果你发现团队 90% 的时间都花在挑剔缩进和变量名上，那你很可能是在让大家把时间浪费在本可以大部分自动化的事情上。写一份风格指南，在提交时用工具强制检查缩进与空格问题，把时间花在更高价值的问题上。我并不是要贬低一致风格的重要性。恰恰相反，拥有一致而地道的风格，是让代码库易于阅读与理解的最简单方法之一。不过，如果你把全部代码审查时间都花在这些浅显的事情上，那就问问自己：你是不是在回避那项更难、也更重要的工作 —— 让团队保持认知对齐，并思考更高层的设计。
